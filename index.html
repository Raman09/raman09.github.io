Principles

Six rules I work by

Write only what the source supports.

Every requirement traces back to something someone said or wrote. Where the source is thin, I flag the gap instead of filling it in.

AI drafts, I validate.

I use AI to draft tickets, requirement documents and test cases, then check each output against the source before anyone else sees it. AI saves the typing; the checking stays with me.

Show, then specify.

I build a clickable prototype first and let the ticket point to it instead of describing every element in words. Each ticket gets only the UI that belongs to it.

Never overwrite the current version.

When a change would alter what exists today, the current version stays the default and the change is added as a switch. Reviewers compare both in one place.

Look at how it works live first.

Before I redesign a screen, I check how it behaves in production and design inside the same patterns. I don’t borrow patterns from other flows.

Say what the customer sees.

Release notes and help copy describe what a customer sees or can do, in plain language. Internal work gets one short line.

How I do it

Three workflows, step by step

Messy inputs to build-ready tickets

The structure stays fixed, so developers always know where to look.

  1. Collect the source: meeting notes, reports and requests.
  2. Draft with AI, then check every line against the source.
  3. Use one structure: Summary, Description, Requirement, Acceptance Criteria. A section appears only when the source supports it.
  4. Never invent acceptance criteria. Flag what the source is missing.
  5. Put the product area in the heading so tickets group cleanly.
  6. Keep Requirement to what the assignee has to do, and keep related changes in one ticket.

AI-driven testing with evidence

The agent does the running; I own the review.

  1. Build a test catalog and trace every case to a Jira ticket.
  2. Add regression checks that protect behavior that already works.
  3. Write a protocol an AI agent can follow in a real browser on a staging environment.
  4. The agent reports pass or fail for each case, with evidence.
  5. I review the evidence, not just the verdict.

Prototyping with Claude

Reviewers react to something real before anything is built.

  1. Check how the screen works live and note its patterns.
  2. Build an interactive HTML prototype with Claude.
  3. Keep the current version as the default and add each change as a switch in the same prototype.
  4. Write a minimal ticket that points to the prototype and says which state to render.
  5. Attach only the UI that belongs to that ticket.

Quality

How I catch AI mistakes

Four checks I run before anything AI-generated goes further.

Trace it

Every line of an AI draft has to map to the source. Anything that doesn’t is removed or flagged.

Check the evidence

For test runs, I look at the evidence behind each pass or fail instead of trusting the verdict.

Don’t let it fill gaps

Requirements, acceptance criteria and examples are never added to cover missing information. The gap gets flagged.

Own the output

Nothing AI-generated goes to a developer, a customer or a stakeholder until I’ve checked it.
